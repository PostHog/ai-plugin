# Framework rules

Follow these when integrating PostHog into this framework.

- A missing PostHog configuration must never break the app — read keys optionally (never a required setting, and never with a format check such as a URL rule in an env schema, which a blank value fails at boot), guard init and capture behind their presence, and keep build and boot working with no PostHog environment set — but never silently: in development or debug builds fail loudly, using the language's idiomatic error, with the message "<VAR> variable required by PostHog is missing or un-configured, this causes events to be silently missed. This error stops appearing once <VAR> is configured" (substituting the actual variable name); production stays a no-op. Only client code, in a browser or on a device, raises it as an error. Server-side code (a server, a worker, a module they load) logs that message as a warning outside production and keeps running, because an error there stops the process from booting for anyone without PostHog keys. A process another program launches, such as an MCP server on STDIO, has nobody watching it boot and no development build — it always writes the warning to stderr (never stdout, which can carry the protocol)
- Sending analytics must never fail or stall the app's own work. Where the app waits on a flush, handle any error it raises and keep the wait short. A long-running server or worker whose SDK sends in the background needs no flush after each capture
- Install the SDK with the package manager's add command and the version the SDK docs pin, so it resolves a published release of that major. Never type a version the docs don't show. Leave dependencies this integration did not add at their current versions
- In a monorepo or workspace, install the SDK in the package that imports it, not at the repository root
- Create one server-side client per process at startup and reuse it for every request. In serverless functions and other per-request handlers, flush before the handler returns, or the events are lost
- Identify users with the app's own stable user id, such as a primary key or UUID, never an email or username. Send those as person properties instead. Identify once when the user logs in or signs up, and call `reset()` when they log out
- On a server, identity belongs to the request, never to the process. Where the SDK has middleware or a context for the framework, use it, so events and errors inside the request carry the user. For a signed-out visitor, use a random id kept for the visit and set `$process_person_profile` to false. If the framework integration already sends signed-out events as personless, as the Laravel SDK does, keep its behavior. Never share one id, such as "anonymous", across visitors
- If the app sends a Content-Security-Policy (a meta tag or a response header), extend it for the browser SDK in one change: allow the PostHog hosts, or the reverse proxy, in `script-src` and `connect-src`, and `blob:` in `worker-src` for session replay. A partial change fails silently: the SDK loads, but events or recordings never send
- When one codebase ships several platform targets (Flutter, React Native, Kotlin Multiplatform), initialize PostHog for every target the project ships. One init call often covers only some of them
